## Главная цель

Внутри одного существующего 3D-телефона в hero лендинга показать облегчённую живую HTML-демонстрацию настоящего Mini App:

1. Клиент выбирает заведение и оформляет заказ.
2. Касса принимает этот же заказ.
3. Кухня начинает готовить и завершает заказ.
4. Директор видит обновление показателей.

Корпус телефона остаётся одним и тем же. Меняется только HTML-содержимое его дисплея.

- Показывается одно выбранное заведение.
- В меню отображается 1–2 позиции.
- Checkout показывается как короткое подтверждение без настоящих полей.
- В кассе и кухне показывается одна карточка заказа.
- У директора показывается только главная сводка.

## 6. Встраивание HTML в 3D-телефон

1. Сохранить существующий `.hero-phone` и его 3D-transform.
2. Не создавать новые PNG-телефоны.
3. Не менять корпус между ролями.
4. Сделать `.hero-phone__display` постоянно непрозрачным.
5. Добавить живой HTML-экран `guest`.
6. Разместить `guest`, `cash`, `cook`, `director` внутри одного clip-контейнера дисплея.
7. Подогнать только маску дисплея:
   - `left`;
   - `top`;
   - `width`;
   - `height`;
   - `border-radius`;
   - перспективный `skew`.
8. Использовать container units для внутреннего масштаба.
9. Не масштабировать готовые скриншоты кабинетов.

## 7. Изоляция стилей

Создать отдельный namespace, например:

```text
#heroPhoneDisplay
  .yj-demo
  .yj-demo-screen
  .yj-demo-client
  .yj-demo-cashier
  .yj-demo-kitchen
  .yj-demo-director
```

Правила:

- Все новые стили начинаются с `.yj-demo-*`.
- Все селекторы ограничены корнем `#heroPhoneDisplay`.
- Токены объявляются на `.yj-demo`, например `--demo-bg`, `--demo-accent`.
- Не копируются глобальные правила `:root`, `body`, `*`.
- Не используются общие имена `.app`, `.hero`, `.section`, `.card`, `.button`.
- Реальные `--bw-*` и клиентские токены переводятся в локальные `--demo-*`.
- Стили подключаются отдельным файлом после общих компонентов.

## 8. Общий сценарий

Каноническая цепочка:

```text
created → accepted → cooking → ready
```

Последовательность экранов:

1. Гость видит каталог.
2. Гость выбирает «Шашлычная №1».
3. Открывается компактное меню.
4. Блюдо добавляется в корзину.
5. Показывается итог и действие «Оформить заказ».
6. Заказ №120 создаётся в статусе `created`.
7. Касса видит тот же заказ и принимает его.
8. Статус меняется на `accepted`.
9. Кухня получает тот же заказ.
10. Кухня переводит его в `cooking`.
11. Кухня завершает приготовление.
12. Статус становится `ready`.
13. Директор видит обновлённые показатели.

Ручные табы должны показывать соответствующую точку единого сценария, а не сбрасывать данные. После ручного переключения autoplay можно возобновлять с небольшой задержкой.

При `prefers-reduced-motion: reduce`:

- autoplay отключается;
- движение и счётчики отключаются;
- остаётся ручное переключение;
- полезные изменения цвета и текста сохраняются.

## 10. Риски

### CSS

- Глобальные reset и `:root` из кабинетов могут сломать лендинг.
- Слишком общие классы могут пересечься с текущими `.hero`, `.section`, `.app`.
- Решение: отдельный файл, локальные токены и строгий namespace.

### Масштаб и читаемость

- Настоящие кабинеты рассчитаны на ширину до `480px`.
- Дисплей в текущем наклонённом PNG значительно уже.
- Нельзя просто уменьшить весь кабинет через `transform: scale()`.
- Нужно вручную сократить плотность и оставить только читаемые элементы.

### Геометрия дисплея

- Маска зависит от перспективы растрового корпуса.
- На разных ширинах возможны просветы по краям.
- Требуется отдельная визуальная проверка desktop/tablet/mobile.

### Запечённый клиентский экран

- При прозрачном crossfade может проступать старый растр.
- Фон живого дисплея должен быть непрозрачным во всех состояниях.

### Анимации

- Transform корпуса управляется CSS и pointer-parallax.
- Внутренние экраны не должны перезаписывать transform корпуса.
- Анимировать следует преимущественно `opacity` и `transform`.
- Переходы должны быть прерываемыми.

### Доступность

- Автоматические обновления не должны постоянно засорять `aria-live`.
- Озвучивается только подпись активной стадии.
- Ручные табы остаются настоящими кнопками.
- Сохраняется keyboard-навигация и видимый focus.

### Источники данных

- Каталог заведений находится в лендинге.
- Production Mini App из `main` привязан к одной точке.
- Эти два слоя нужно связать визуально, не выдавая локальный каталог за существующий production-компонент.
