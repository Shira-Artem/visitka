таймингов, устойчивости состояний и mobile-фолбэка **до** начала кода.

## Что изменилось относительно ред. 1

Первая версия плана пинила только акты 2–6, а Hero был обычным, не закреплённым потоком —
на границе Hero → Story был риск скачка/дублирования телефона. Это неприемлемо (требование 1).
Новая архитектура: **один непрерывный sticky-объект от начала Hero до конца акта «Директор»**.
Также: неравные длительности актов (требование 2), явная детерминированность состояний
(требование 4) и hysteresis на границах (требование 5), минимум контента на акт (требование 7),
сохранённый ручной переключатель ролей (требование 8), упрощённый mobile-фолбэк без клонов
телефона (требование 6), и раздельные фазы «построить» / «проверить» / «вычистить старое»
(требования 3, 9).

Ключевое отличие от ред. 1: телефон **никогда не переносится между секциями** — с самого верха
страницы (`scrollY=0`) он уже находится внутри `.story__stage`, просто в этот момент
`position: sticky` ещё не «прилипло» (элемент в нормальном потоке в начале трека, визуально —
ровно там же, где сегодня стоит hero-телефон). При скролле трек начинает уходить вверх, стейдж
залипает — никакого визуального скачка, дублирования или layout-шифта, потому что это один и тот
же DOM-узел от первого кадра до конца акта «Директор». Разлипание (переход к `.final`) — осознанный
финальный жест (лёгкий scale/fade телефона), не баг.

## Веса актов и общая высота трека (требование 2)

Единый источник правды — массив в `main.js`, а не хардкод в CSS (без сборки нечем шарить константы
между файлами, поэтому высоту трека **вычисляет JS** из этого же массива):

```js
var STORY_ACTS = [
  { id:'hero',     vh:70,  states:['idle'] },
  { id:'how',      vh:130, states:['venue','menu','checkout','success'] }, // сцены гостя, уже есть
  { id:'checkout', vh:65,  states:['checkout'] },   // держим сцену checkout, меняется только подпись
  { id:'cash',     vh:65,  states:['new','accepted'] },
  { id:'kitchen',  vh:90,  states:['new','cooking','ready'] },
  { id:'director', vh:75,  states:['default'] }
];
// сумма = 495svh — попадает в целевой диапазон 450–520svh
```

`storyTrack.style.height = totalVh + 'svh'` выставляется в JS при инициализации и на resize.
Границы каждого акта в пикселях считаются как доля от `track.scrollHeight - viewportHeight`,
пропорционально `vh`-весам — не поровну. Больше всего «веса» — у «Как это работает» (4 сцены
гостя) и «Кухни» (3 состояния): это самые насыщенные по контенту акты, они и должны идти дольше.
495svh — стартовая цифра; после визуальной проверки (фаза B ниже) её можно подстроить под
реальное ощущение «20–30 секунд спокойного скролла» на тестовом устройстве.

## Детерминированные состояния (требование 4)

Сейчас `enterRole()` (hero-demo.js:306–353) одновременно и переключает DOM, и планирует следующий
автоплей-шаг через `scheduleNext()`/`queue()` — состояние «сборка» размазана по цепочке таймеров.
Это ломается при быстром или прыжковом скролле (например, перетаскивание скроллбара сразу в конец).

Рефакторинг: выделить из `enterRole` чистую синхронную функцию `applyState(role, subState)`,
которая **идемпотентно** приводит DOM к запрошенному состоянию за один вызов — без чтения
предыдущего состояния и без прохождения промежуточных шагов:
- Начинается с `clearTimers()` (уже существует, чистит все `setTimeout`/`setInterval`/rAF-id).
- Останавливает любой незавершённый rAF-твин (например, счётчики директора, если человек
  проскроллил акт «Директор» наполовину и тут же вылетел вперёd).
- Далее — прямое присвоение классов/атрибутов/текста, соответствующих ИМЕННО `{role, subState}`
  (не «прокрутка» через cash→cook→director по пути, если скролл прыгнул из «how» сразу в
  «director»).
- Косметический crossfade (150–250мс CSS transition) на смену экрана — чисто визуальный, не
  завязан на бизнес-логику/тайминг.

`window.YJ_HERO_DEMO = { applyState }` — единственная публичная точка входа для scroll-контроллера
и для ручного переключателя ролей. Старая цепочка автоплея (`scheduleNext`) остаётся в файле только
как опциональный «отдых» ДО того, как пользователь начал скроллить сюда (акт hero, лёгкое дыхание),
и полностью отключается, как только стартует управление скроллом.

## Hysteresis на границах сегментов (требование 5)

И на уровне актов (6 сегментов), и на уровне под-состояний внутри акта (2–4 сцены) используется
общий helper с полосой нечувствительности, а не «сырое» деление прогресса на N равных кусков:

```js
function pickIndex(rawFloat, lastIndex, count, margin) {
  var rounded = Math.round(rawFloat);
  if (rounded === lastIndex) return lastIndex;
  var movingForward = rounded > lastIndex;
  var threshold = lastIndex + (movingForward ? 1 - margin : -(1 - margin));
  var crossed = movingForward ? rawFloat >= threshold : rawFloat <= threshold;
  return crossed ? clamp(rounded, 0, count - 1) : lastIndex;
}
```

`margin` ≈ 0.12 (12% буфер вокруг каждой границы). Один и тот же `pickIndex` используется и для
выбора активного акта, и для под-состояния внутри акта — при медленном скролле туда-сюда рядом с
границей состояние не дёргается, потому что нужно реально «перейти» границу с запасом, а не
коснуться её.

## Ручной переключатель ролей во время истории (требование 8)

`.hero-role-switch` переезжает из старого hero внутрь `.story__phone-col` и остаётся видимым и
кликабельным на протяжении всего пина (не только в акте 1). Поведение:

1. Пока пользователь просто скроллит — кнопки лишь отражают активную роль (`aria-pressed`),
   `initStoryScroll()` сам вызывает `applyState()` по вычисленному акту/под-состоянию.
2. Клик по кнопке роли → `manualOverride = true`, запоминаем `overrideActIndex` (текущий индекс
   акта на момент клика) и вызываем `applyState(role, defaultSubForRole)` напрямую — пользователь
   свободно «застревает» в этой роли и может, например, потыкать кнопки внутри кабинета кассы,
   пока `manualOverride` активен (скролл-контроллер не перезаписывает состояние).
3. На каждый тик скролла контроллер сверяет свежевычисленный индекс акта с `overrideActIndex`:
   как только они расходятся (человек доскроллил до следующего — или предыдущего — акта),
   `manualOverride` сбрасывается и управление автоматически возвращается скроллу.

## Mobile / reduced-motion — один телефон, без клонов (требование 6)

Ревизия 1 ошибочно подразумевала «раскладку актов как отдельных секций» без явного запрета на
дублирование мокапа. Уточнение: телефон **всегда один и тот же DOM-узел**, дублирования нет ни на
десктопе, ни на мобиле.

Ниже брейкпоинта `matchMedia('(min-width:981px)')` (тот же, что уже используется для параллакса,
main.js:417) или при `prefers-reduced-motion: reduce`:
- `.story__track` получает `height:auto`, `position:sticky` со `.story__stage` **снимается** —
  никакого scroll-jacking и никакой гигантской высоты трека на маленьком экране.
- Тот же самый `#heroDemo` рендерится один раз в верхней части `.story` (обычный поток, не залипает).
- Под ним — последовательные короткие карточки-акты (`.story__mobile-card`, по одной на каждый акт
  из таблицы выше, без под-состояний — сразу целевой финальный вид).
- `IntersectionObserver` (тот же паттерн, что уже был в `initShowcase`, main.js:94–105, и в самом
  hero-demo.js:442–461) следит за карточками: как только карточка пересекает ~50% вьюпорта,
  вызывается `applyState()` с состоянием, привязанным к этой карточке через `data-act`/`data-sub`.
- Один телефон, один слушатель, без клонирования мокапа под каждый акт.
